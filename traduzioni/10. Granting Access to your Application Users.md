# Amazon Cognito
Bene, Amazon Cognito. Ne abbiamo dato una definizione ad alto livello, ora entriamo nei dettagli. Cos'è Amazon Cognito? Innanzitutto, Amazon Cognito è un identity store. Hai quindi un posto in cui memorizzare username e password dei tuoi utenti, e i dati personali relativi a ciascun utente. È comodo perché, per quanto mi riguarda personalmente, quando nella mia vita precedente facevo lo sviluppatore, non mi piaceva per niente scrivere codice di autenticazione, dover gestire questi utenti, memorizzarli e preoccuparmi di tutto questo, giusto? Cognito è ottimo per questo genere di cose.

Puoi avere tutto questo fornito da Cognito per le tue web app e le tue app mobile. E offre anche qualcosa chiamato hosted UI: puoi creare un identity store per memorizzare chi sono i tuoi utenti, e tutta la parte di storage è gestita da AWS. Ma in più, usando la hosted UI, la schermata di login, la pagina di password dimenticata e tutto il resto possono essere ospitate da AWS e messe a tua disposizione, e tu devi solo integrarle nella tua app. È davvero comodo se non hai intenzione di scrivere queste cose da solo. Soprattutto se sei una piccola realtà, un team molto piccolo, o magari stai cercando di rilasciare un'app proof-of-concept e non vuoi faticare a scrivere queste cose da te: in questi casi è utilissimo. Inoltre, ti permette anche di controllare l'accesso alle risorse AWS.

Quindi hai l'identity store, cioè i tuoi utenti che fanno login nella tua app, ma c'è anche un'altra funzionalità di Cognito che può aiutarti a controllare l'accesso alle risorse AWS, il che può essere utile quando usi cose come le identità federate. Inoltre, rispetta diversi programmi di compliance, quindi assicurati di consultare la documentazione sulla compliance di Cognito per verificare che soddisfi le tue esigenze.

Bene, abbiamo quindi questi due concetti, questi due componenti di Amazon Cognito. Abbiamo gli user pool, e gli user pool ti forniscono l'autenticazione, il sign-in/sign-up, giusto? Memorizzano i tuoi utenti e forniscono il login se vuoi usare la hosted UI. Tutto questo viene dallo user pool. Poi c'è la domanda: devi concedere a quell'utente delle chiavi AWS? Questo utente deve poter accedere a risorse AWS? Se la risposta è sì, allora userai un identity pool.

Quindi, lo user pool serve per fare login nella tua app. Potrebbe non avere nulla a che fare con le chiavi AWS: voglio semplicemente autenticare un utente nella mia applicazione. Un identity pool, invece, serve quando voglio concedere agli utenti delle chiavi AWS, in modo che possano fare richieste alle API AWS. Ora, Amazon Cognito si integra con Amazon API Gateway. Puoi scegliere Amazon Cognito come authorizer per Amazon API Gateway. Puoi configurare i tuoi utenti e registrarli nel tuo user pool, e poi creare quello che si chiama app client. A quel punto puoi usare quell'app client e integrarlo con API Gateway, così le persone fanno login con Cognito e le loro identità vengono inviate ad API Gateway, che ha una relazione con Cognito. Cognito viene configurato come authorizer e può quindi verificare che quell'utente possa accedere alle tue risorse di back-end.

Con API Gateway puoi usare anche i Lambda authorizer, che sarebbero il tuo codice personalizzato per l'autorizzazione. Quindi Cognito non è l'unica opzione: puoi anche scrivere il tuo codice personalizzato per la tua applicazione. E poi abbiamo qui il tuo identity pool. L'identity pool fornisce credenziali AWS, il che, di nuovo, può essere utile quando usi identità federate. Per esempio, ho un utente che ha fatto login con Facebook o con Google e voglio permettergli di ottenere credenziali AWS. Posso farlo con un identity pool. Inoltre ti permette di consentire a utenti guest non autenticati, o anonimi, di avere accesso a credenziali temporanee per fare richieste alle API AWS.

Dietro le quinte, questo si integra con IAM e AWS STS per ottenere quelle credenziali temporanee da fornire agli utenti. Quindi queste due cose sono componenti diversi, ma puoi usarli insieme. Usarli insieme può essere un ottimo modo per avere utenti che fanno login nella tua app e che poi hanno bisogno di credenziali AWS per poter svolgere delle attività.

Quindi questi due componenti, lo user pool e l'identity pool, possono essere usati singolarmente, ma non è obbligatorio: possono anche essere usati insieme.

# Gestione dell'accesso degli utenti
Ok, vediamo più nel dettaglio come gestire l'accesso degli utenti con Cognito. A questo punto parleremo degli user pool. Quando crei uno user pool, puoi crearlo per il sign-up e per il sign-in, giusto? Quindi: come mi registro nello user pool e creo un account utente, e poi voglio anche poter fare sign-in.

Gli user pool possono gestire entrambe le cose. Quando crei uno user pool puoi definire alcuni dei processi e degli attributi associati a questo utente. Per esempio, voglio verificare l'email o il numero di telefono quando l'utente si registra? È molto comune voler verificare che qualcuno ti abbia fornito un indirizzo email o un numero di telefono validi al momento della registrazione, prima di verificarne l'account. Perché così, se dovrà usare la funzione di password dimenticata o di cambio password, sai che sarà in grado di farlo.

Puoi anche decidere come gestire l'MFA. Vuoi che l'autenticazione a più fattori sia obbligatoria per tutti nel tuo account? Puoi imporre delle password policy. Vuoi, per esempio, otto caratteri e un carattere speciale? Saranno sei? Insomma, quali sono i tuoi requisiti per le password? Puoi anche stabilire quali authentication flow esistono per il tuo user pool. Anche qui, il modo in cui gestisci queste cose dipende dal singolo caso d'uso. Ma c'è anche il concetto di attributi associati all'utente. Per esempio l'indirizzo email, lo username, il numero di telefono: puoi stabilire quali attributi sono obbligatori e quali no.

Per quanto riguarda gli attributi, abbiamo attributi standard come l'email e il nome, ma puoi anche scegliere di includere attributi personalizzati, come un nickname o un'immagine, giusto? Puoi quindi personalizzare il tuo user pool come ti serve. Puoi organizzare i tuoi utenti in gruppi, che rappresentano i diversi tipi di utenti all'interno della tua app. Un esempio: magari hai gli utenti finali e poi hai gli amministratori. Se hai un'applicazione di blog, per esempio, hai gli utenti finali, cioè le persone che leggono i blog e interagiscono con il tuo blog, ma potresti avere anche gli amministratori del blog, persone che possono entrare e moderare il blog, aggiungere nuovi contenuti e cose del genere.

In Cognito gli utenti possono appartenere a più gruppi. E poi c'è anche il concetto di scope. Lo scope ti permette di determinare il livello di accesso alle tue risorse che un'applicazione può avere. Quindi in Cognito puoi personalizzare anche lo scope e il livello di accesso a quelle risorse.

# Concedere l'accesso alla tua applicazione con gli user pool
Continuiamo a parlare di come concedere l'accesso alla tua applicazione con gli user pool. Con Amazon Cognito puoi scegliere di usare i JSON web token.

I token di Cognito sono in formato JWT. Vediamo quindi com'è fatto questo formato JWT. Qui abbiamo un header, e in questo header c'è il key id. Poi c'è l'algoritmo, cioè quale algoritmo verrà usato. E poi abbiamo il payload.

Il payload contiene alcune informazioni codificate sulla richiesta, come l'auth time, lo username Cognito, la scadenza, il nome, l'email e cose simili. Poi c'è la firma (signature), che viene calcolata a partire dall'header e dal payload. Questi token vengono poi inviati insieme alle tue richieste effettive. Verranno decodificati e serviranno a determinare se sei effettivamente autorizzato o meno a usare l'applicazione a cui stai cercando di accedere.

Diamo quindi un'occhiata al workflow di utilizzo di questi token con Cognito. Qui abbiamo la nostra applicazione, e nella nostra applicazione ci sono utenti che fanno login. L'utente fornisce le proprie credenziali e si autentica con Cognito nello user pool. Lo user pool restituisce quindi i token di refresh, di accesso e ID. Restituisce cioè questi token JWT all'app. L'app usa poi quei token per accedere alle tue risorse, ad esempio le tue API di backend e cose simili.

L'ID token contiene dettagli sull'utente, mentre l'access token contiene dettagli su ciò a cui l'utente può accedere, senza però condividere i dettagli dell'identità all'interno del token.

# Concedere l'accesso alla tua applicazione con gli identity pool
Abbiamo appena visto gli user pool. Ora parliamo degli identity pool. In Cognito, un identity pool è diverso da uno user pool.

In un identity pool hai dei ruoli associati a degli identity provider. Hai quindi un identity provider, come dicevo prima Facebook, Google, Amazon, e il tuo utente si autentica con questo identity provider. In questo modo dimostra di essere chi dice di essere, giusto? Si autentica con l'identity provider.

L'app invia poi un token di autenticazione a Cognito, e Cognito sa che provieni da quell'identity provider. E tu hai configurato dei ruoli che puoi mappare su queste identità. A quel punto l'identity pool restituisce delle credenziali AWS associate al ruolo. Le credenziali avranno i permessi che hai definito nel ruolo, e la tua applicazione potrà usarle per inviare richieste alle API AWS.

L'identity pool in sé non contiene nessuna delle informazioni di identità relative al login o alla password dell'utente o cose simili. Quelle provengono dal tuo identity provider e sono interamente memorizzate lì. Quindi questo è un modo per distribuire credenziali AWS senza doverti preoccupare di mantenere le informazioni dell'utente da qualche parte, come invece fai con un gruppo di utenti o se lo fai da solo. Ecco cosa sono gli identity pool.

# Proteggere l'accesso alle API
Ok, un paio di moduli fa abbiamo creato un'API, ma era aperta al pubblico. Ho detto che Cognito ti permette di autenticare un'API in API Gateway, ma vediamo un po' più nel dettaglio come funziona davvero.

In questo diagramma ci sono due lati diversi. C'è lo sviluppatore che configura l'API e l'autorizzazione, e poi c'è l'utente che userà effettivamente questa API. Prima di tutto c'è lo sviluppatore, cioè tu, giusto? Crei uno user pool e lo configuri. È lì che stabilisci quali attributi vuoi e lo scope, e crei il tuo app client. Poi, una volta creato lo user pool, in API Gateway puoi scegliere quello user pool come authorizer. Questo significa che devo assicurarmi che chiunque acceda a questa API sia prima passato da Cognito e si sia autenticato.

Quindi integri la tua API con il tuo user pool Cognito, e questo vale per le REST API. Tra poco vedremo un esempio con una HTTP API. Dall'altro lato, una volta configurato tutto, hai un utente finale che fa login con la tua applicazione. Puoi avere la tua applicazione con la tua pagina di login e poi usare le API di Cognito per l'autenticazione sul backend, oppure puoi usare l'hosted API di Cognito, in cui è Cognito a fornirti la pagina di login. Dipende solo da cosa vuoi fare e da qual è il tuo caso d'uso. Quindi l'utente finale si autentica in qualche modo con la tua applicazione, giusto? E Cognito le restituisce il token JWT, che viene poi inserito nella richiesta per accedere ad Amazon API Gateway.

Da lì potrai accedere ai servizi AWS di backend. API Gateway fa da cancello tra l'utente finale e le tue risorse di backend. Una soluzione alternativa a Cognito per proteggere le tue API è usare un Lambda authorizer. Quindi, se non vuoi usare Cognito ma hai i tuoi metodi di autenticazione, puoi usare una funzione Lambda per questo.

In questo caso le tue applicazioni fanno richieste ad API Gateway e includono il bearer token con gli header di autorizzazione che indicano chi è questa persona. Da qui prendi quella richiesta ed esegui questa funzione Lambda; la funzione Lambda avrà la propria logica personalizzata per determinare se questa persona è chi dice di essere. Qui potresti usare JWT oppure OAuth. E poi riporterà se quell'utente è effettivamente autorizzato o meno.

A quel punto API Gateway valuterà la policy, cioè la IAM policy e il principal restituiti dalla funzione Lambda, e determinerà se l'accesso è consentito o negato. Se è consentito, potrai procedere e accedere alle risorse AWS. Questa è quindi un'alternativa all'uso di Cognito come authorizer per API Gateway.
